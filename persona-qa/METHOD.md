# 지표 정의서 — 이 숫자들은 어떻게 계산됐나

> 발표에서 "그 %는 뭘 나눈 건가요"를 받았을 때 펼칠 문서.
> 기계 판독본은 각 회차의 `metrics.json`, 생성 스크립트는 [`../scripts/07_metrics.py`](scripts/07_metrics.py) (LLM 호출 없음).

## 한 문장으로

**모든 %는 LLM 판정자가 문항마다 붙인 라벨을 센 것이다.** 커버리지 65.0%는
`판정 '정상' 39건 ÷ 전체 60건`이고, 그 '정상'은 `claude-haiku-4-5`가 답변을 읽고 5개 라벨 중
하나를 고른 결과다. 이 문서의 나머지는 전부 이 문장의 각주다.

## 측정 파이프라인 — 숫자가 만들어지는 경로

```
01 샘플링      실제 인구 분포 기반 페르소나 추출 (연령 5구간 × 성별, 시드 고정)
02 질문 생성   페르소나 서사만 주고 질문 3개 생성 — 제품 카탈로그는 주지 않는다
03 실측        headless Claude + 원격 MCP(ask-seoul.kr/mcp)로 질문을 그대로 던짐
               → 답변 본문 + 툴 호출 경로를 기록
04 채점        LLM 판정자가 답변을 읽고 라벨·grounded·usefulness·gap 부여
05 집계        라벨을 세서 % 계산                     ← 리포트의 모든 숫자가 여기서 나온다
07 근거화      분자·분모·신뢰구간·교차검증을 metrics.json 으로 고정
```

**02에서 카탈로그를 숨기는 것이 이 측정의 핵심 설계다.** 제품 목록을 알려주고 질문을 만들면
"우리가 가진 데이터로 답할 수 있는 질문"만 생성돼 커버리지 측정이 무의미해진다. 카탈로그를
모르는 상태에서 나온 질문이라야 "진짜 수요 중 몇 %를 커버하나"를 잴 수 있다.

## 지표 정의

### 커버리지 — 두 가지 정의가 있고, 둘 다 계산했다

| | 라벨 기반 (리포트의 '커버리지') | 툴경로 기반 |
|---|---|---|
| 묻는 것 | **질문에 답했나** | **제품에 도달했나** |
| 분자 | 판정 라벨이 `정상`인 문항 수 | `query_product`·`run_pattern`·`preview_product` 중 하나라도 호출한 문항 수 |
| 분모 | 전체 문항 수 | 전체 문항 수 |
| 판단 주체 | LLM 판정자 (주관) | 툴 호출 로그 (객관) |
| 계산 위치 | `05_report.py:52` | `07_metrics.py` |

`PLAN.md §3-04`는 원래 커버리지를 **툴경로 기반**으로 정의했는데, 실제 구현(`05_report.py`)은
**라벨 기반**이다. 이 불일치를 덮지 않고 둘 다 산출해 교차검증한다.

### 나머지 지표

| 지표 | 정의 | 계산 | 위치 |
|---|---|---|---|
| **근거성** | 판정자가 `grounded=true`를 준 비율. "조회 데이터에 근거했거나 한계를 명시함" | `true 건수 ÷ 전체` | `05_report.py:50` |
| **유용성** | 판정자가 매긴 1~5 정수의 산술평균 | `점수 합 ÷ 문항 수` | `05_report.py:51` |
| **간극(gap)** | 답하지 못한 원인이 데이터 쪽이면 판정자가 한 줄로 서술. 자유 텍스트라 자동 집계는 빈도수만 | `Counter(gap)` | `05_report.py:68` |

### 신뢰구간

비율 지표는 **Wilson 점수구간 95%**를 함께 낸다. n=60에서 65%의 오차범위는 ±12%p 수준이라,
신뢰구간 없이 "65% vs 48%"를 비교하면 과잉 해석이 된다. 유용성은 평균 ± 1.96·SE.

## 회차별 실측 수치 — 전부 분자/분모/신뢰구간 병기

| | 1차 (8/11) | 2차 (8/12) | 3차 (8/12) |
|---|---|---|---|
| 문항 / 페르소나 | 231 / 77명 | 60 / 20명 | 60 / 20명 |
| **커버리지(라벨)** | 51.5% (119/231)<br>CI 45.1~57.9 | 48.3% (29/60)<br>CI 36.2~60.7 | **65.0% (39/60)**<br>CI 52.4~75.8 |
| **커버리지(툴경로)** | 75.8% (175/231)<br>CI 69.8~80.8 | 75.0% (45/60)<br>CI 62.8~84.2 | **83.3% (50/60)**<br>CI 72.0~90.7 |
| **근거성** | 92.6% (214/231)<br>CI 88.5~95.4 | 96.7% (58/60)<br>CI 88.6~99.1 | **100% (60/60)**<br>CI 94.0~100 |
| **유용성** | 3.13 (합 722/231)<br>sd 0.92 · CI 3.01~3.24 | 3.05 (합 183/60)<br>sd 0.75 · CI 2.86~3.24 | 3.18 (합 191/60)<br>sd 0.72 · CI 3.00~3.37 |

**신뢰구간을 보면 2차와 3차의 커버리지 차이(48.3 vs 65.0)는 구간이 겹친다**(36.2~60.7 vs
52.4~75.8). 표본 60건으로는 "3차가 확실히 더 낫다"고 단정할 수 없다는 뜻이다.

## 교차검증 ① — 두 커버리지 정의의 차이가 곧 데이터 간극의 실체

3차 기준: 툴경로 83.3% − 라벨 65.0% = **18.3%p**. 이 구간이 무엇인지 2×2로 분해하면:

| | 데이터 조회함 | 조회 안 함 |
|---|---|---|
| **판정 '정상'** | 39 | 0 |
| **판정 '정상' 아님** | **11** ← 여기 | 10 |

- **정상 & 미조회 = 0건** — 판정자가 "조회도 안 했는데 정상"을 준 적이 없다.
  라벨이 툴 로그와 모순되지 않는다는 뜻으로, **판정자 신뢰도의 간접 증거**다.
- **비정상 & 조회함 = 11건** — **제품엔 닿았는데 질문은 해결 못 한 구간.**
  "상권 데이터는 찾았지만 일식 업태 동별 통계는 없음" 같은 경우다. 제품 부재가 아니라
  **세분화 부족**이 원인이라, 백로그 우선순위가 "새 제품"이 아니라 "축 추가"임을 가리킨다.
- **비정상 & 미조회 = 10건** — 애초에 해당 제품이 없어서 조회조차 못 한 진짜 공백.

세 회차 전부:

| | 정상&조회 | 정상&미조회 | 비정상&조회 | 비정상&미조회 | 두 정의 일치율 |
|---|---|---|---|---|---|
| 1차 | 116 | 3 | 59 | 53 | 73.2% |
| 2차 | 29 | 0 | 16 | 15 | 73.3% |
| 3차 | 39 | 0 | 11 | 10 | 81.7% |

## 교차검증 ② — 측정 격리도 (1차 수치를 신뢰하기 어려운 이유)

`03_run_queries.py`는 `--allowedTools mcp__askseoul__*`로 MCP만 허용하려 했지만, 실행 로그에는
CLI 로컬 툴 호출이 남아 있다. 로컬 툴이 답변에 개입했다면 "MCP 데이터로 답했다"는 전제가 흔들린다.

| | 로컬 툴이 개입한 문항 | 어떤 툴 | MCP 미호출 문항 |
|---|---|---|---|
| **1차** | **35.5% (82/231)** | Bash 73 · PowerShell 20 · Agent 14 · Write 11 · Grep 11 · Read 9 | 10.4% |
| 2차 | 3.3% (2/60) | Bash 2 · Grep 1 | 1.7% |
| 3차 | 6.7% (4/60) | Bash 4 · Grep 1 · PowerShell 1 · Write 1 | 0% |

**1차는 3분의 1 이상이 MCP 밖 툴을 썼다.** 1차 수치가 흔들린다는 객관적 근거이고,
2·3차에서 격리가 크게 개선됐다는 근거이기도 하다.
(`ToolSearch`·`AskUserQuestion`은 CLI 자체 기능이라 오염에서 제외했다 —
전자는 MCP 툴 스키마를 불러오는 정상 경로, 후자는 '되물음' 판정 그 자체다.)

## 판정자 — 누가, 무엇을 보고 매겼나

| | |
|---|---|
| 모델 | **`claude-haiku-4-5-20251001`** (1·2·3차 전부 동일) |
| 근거 | [`04_judge.py:10`](scripts/04_judge.py#L10) `MODEL` 상수 |
| ⚠️ 주의 | 같은 파일 1행 주석은 `claude-sonnet-5`라고 적혀 있으나 **코드가 정본**. 발표에서 "sonnet이 채점했다"고 말하면 틀린다 |
| 입력 | 질문자 프로필 + 질문 + 툴 호출 경로 + **답변 본문 앞 4000자** |
| 출력 | `{"verdict","grounded","usefulness","gap"}` JSON 한 줄 |
| 라벨 | `정상` / `되물음` / `데이터없음` / `환각의심` / `오류` |
| 실행 | `claude -p --output-format json`, 문항당 1회 |

**판정자를 haiku로 고정한 것은 의도적이다.** 회차마다 판정자를 바꾸면 라벨 분포가 판정자 때문에
움직인 건지 서비스 때문에 움직인 건지 갈라낼 수 없다. 판정 품질보다 **회차 간 비교 가능성**을
택했다.

## 알려진 한계 — 먼저 말하는 편이 낫다

1. **판정 신뢰도를 측정한 적이 없다.** 같은 답변을 두 번 채점하면 같은 라벨이 나오는지,
   사람이 봐도 같은 판정인지 잰 적이 없다. 현재로선 판정자를 믿는 것 외에 근거가 없다.
   → 위 교차검증 ①의 "정상 & 미조회 = 0건"이 유일한 간접 증거다.
2. **판정 이유를 저장하지 않는다.** 라벨만 남아서 "이 문항은 왜 데이터없음인가"에
   답변 본문을 직접 읽어야 한다.
3. **유용성은 1~5 정수 평균이라 등간성이 없다.** 3.18과 3.05의 0.13 차이는 의미를 두기 어렵다.
   순서통계로만 읽는 것이 안전하다.
4. **회차 간 조건이 다르다** — 모델·질문·카탈로그가 회차마다 바뀌었다. 자세한 것은
   [README.md](out/README.md)의 "회차 간 직접 비교가 안 되는 이유".
5. **gap 은 자유 텍스트다.** 같은 원인이 다른 문장으로 적혀 빈도 집계가 과소계상된다.
