# 0003 — 공개 식별자: URL 에 무엇을 쓰나 (테이블명 → `product_id`)

- 상태: 초안 (합의 대기)
- 당사자: marketplace(@yooseongjin527) · K-Skill(@masondev1024) · 콘솔(@Exisign)
- 관련: ASK-Seoul-Serving#20(공개 배포 준비) · ASAC-DAG#476 ②(URL 결정) ·
  ASAC-DAG#642(`/skill/v1` 경로 분리) · decision/0001 C-6·C-10

## 왜

지금 게이트웨이는 **같은 제품을 두 이름으로 부른다.**

```
GET /api/data/gold_culture_activity_by_dong     ← 물리 테이블명
GET /v1/products/culture_activity_by_dong       ← 계약 id
```

그리고 그 테이블명은 도메인마다 접두사가 갈린다 — 실측 62종 중 `gold_` 40종, `d1_` 22종.
외부 소비자에게 둘 다 뜻이 없다. `gold_` 는 창고 메달리온 계층이고 `d1_` 은 저장소 이름이라,
**우리 내부 구조를 URL 로 새어 보내는 것**이다. 접두사가 갈린 건 그 결과이지 원인이 아니다.

이걸 지금 정하는 이유는 셋이다.

1. **URL 은 정해지면 못 바꾼다.** 소비자가 붙은 뒤의 변경은 파손이다(#476 ② 결정과 같은 근거).
2. **아직 공개 배포 전이라 깨질 소비자가 없다.** 바꾸는 비용이 앞으로 가장 싼 시점이다.
3. **K-Skill·MCP 작업이 지금 시작된다.** 새 소비자가 어느 이름에 붙느냐가 여기서 갈린다.

## 결정

### D-1. 공개 식별자는 `product_id` 다

`/api/data/<id>`·`/api/preview/<id>` 도 `/v1/*`·`/skill/v1/*` 과 같은 식별자를 받는다.

이유는 이미 코드에 적혀 있다(`src/v1.js` 머리주석) — **테이블명은 물리 이름이라 바뀔 수
있고, `product_id` 는 계약(`meta.serving`)이 보증한다.** 새 경로 둘이 이미 그 판단으로
서 있는데 옛 경로만 물리명을 노출하는 상태다.

실측으로 쓸 수 있음을 확인했다(로컬 D1 `_catalog` 62종):

| | 값 | 접두사 |
|---|---|---|
| `name` | `gold_culture_activity_by_dong` · `d1_flow_monthly` | `gold_` 40 · `d1_` 22 로 갈림 |
| **`product_id`** | `culture_activity_by_dong` · `commerce_flow_monthly` | **없음. 62/62 존재, 중복 0** |

`product_id` 의 앞 토막은 도메인이라(`culture_`·`commerce_`·`weather_`) 뜻이 있는
네임스페이스다 — 소비자가 "이건 어느 도메인 제품인가"를 URL 만 보고 안다.

### D-2. 테이블명은 과도기 동안 **별칭으로 계속 받는다**

`_catalog` 한 행에 두 값이 다 있으므로 조회 한 번으로 끝난다.

```js
// 지금:  WHERE name = ?
// 이후:  WHERE (product_id = ? OR name = ?)
```

끊는 시점은 이 문서가 아니라 **공개 배포 이후 별도 판단**이다(#20). 배포 전에 끊으면
지금 로컬로 붙어 있는 팀 내부 소비자가 먼저 깨진다.

### D-3. 카탈로그 응답은 두 값을 **모두** 싣는다

`/api/catalog` 는 이미 `name`·`product_id` 를 함께 준다. 이걸 유지한다 — 소비자가 옮겨
탈 근거가 응답 안에 있어야 하고, 콘솔·디버깅은 물리명이 필요하다.

문서(`llms.txt`·`openapi.json`·`docs.html`)의 **예시는 `product_id` 로 바꾼다.** 사람과
에이전트가 먼저 보는 건 예시라, 여기가 안 바뀌면 결정이 없는 것과 같다.

### D-4. 관측(`_request_log.table_name`)에는 **해석된 물리 테이블명**을 남긴다

요청에 무엇이 왔든 실제로 읽은 표를 기록한다. 콘솔의 기존 질의(`GROUP BY table_name`)가
그대로 서고, 별칭 때문에 같은 제품이 두 줄로 갈리지 않는다(0001 C-10 의 유실 검증과 같은
이유 — 관측 축이 갈리면 "얼마나 쓰이나"를 못 센다).

요청 원문이 필요하면 그건 `route` 가 아니라 별도 축이며, **값이 아니라 축만**이라는
0001 C-6 을 그대로 따른다.

## 검토한 대안

### `get_` 로 전 도메인 통일 — 채택하지 않음

이 문서를 쓰게 만든 최초 제안이다. 접두사가 갈린 게 문제라는 **진단은 맞지만** 처방이
어긋난다.

- **메서드가 이미 GET 이다.** `GET /api/data/get_flow_monthly` 는 같은 말을 두 번 한다.
- **뜻이 없다.** `gold_`·`d1_` 은 적어도 내부에서는 뜻이 있는 접두사다. `get_` 은 어디서도
  뜻이 없어서, 의미 없는 접두사를 의미 없는 접두사로 바꾸는 교환이 된다.
- **유지 비용이 는다.** 도메인이 테이블을 새로 낼 때마다 "공개용 이름"을 하나 더 짓고
  맞춰야 한다 — `product_id` 는 계약이 이미 보증하는 값이라 그 일이 없다.
- 목적이 "내부 어휘를 URL 에서 없애기"라면 **접두사를 없애는 쪽**이 곧장 그 목적이다.

### 접두사만 떼서 `/api/data/flow_monthly` — 채택하지 않음

`product_id` 와 거의 같아 보이지만 **도메인 토막이 빠져 충돌한다.** 예: 여러 도메인이
`event_schedule`·`hourly` 같은 흔한 이름을 쓰면 전역 유일성이 깨진다. `product_id` 는
도메인 접두로 그 문제를 이미 풀어 뒀다.

### 테이블명 자체를 도메인들이 개명 — 채택하지 않음

가장 근본적이지만 **비용이 다른 레포·6개 도메인의 dbt 계약에 걸린다.** 창고 안에서
`gold_` 는 계층 표시로 제 역할을 하고 있어, 외부 표기 하나 때문에 내부 규약을 뒤집는 건
`Z-5`("물리 경로 통일 시도 = 위반", ASK-Seoul#78)와 같은 종류의 과잉이다. 게이트웨이가
매핑하면 되는 일이다.

## 영향 범위 (실측)

| 대상 | 규모 | 성격 |
|---|---|---|
| `src/index.js` | 2곳 (`handlePreview`·`handleData` 의 `WHERE name = ?`) | 한 줄씩 |
| `public/column-docs.json` | 14종 키 | 키 이름 교체 (또는 조회 시 매핑) |
| `public/llms.txt`·`openapi.json`·`docs.html`·`index.html` | 예시 7건 | 문구 |
| `_request_log` | 없음 | D-4 로 현행 유지 |
| `/v1/*`·`/skill/v1/*` | 없음 | 이미 `product_id` |

**소비자 파손 0** — 별칭(D-2)으로 기존 호출이 그대로 산다.

## 되돌리기

`WHERE (product_id = ? OR name = ?)` 를 원래대로 되돌리면 끝이다. 별칭 기간 중에는 어느
쪽도 안 깨지므로, 되돌림의 비용은 문서·예시 문구뿐이다.
