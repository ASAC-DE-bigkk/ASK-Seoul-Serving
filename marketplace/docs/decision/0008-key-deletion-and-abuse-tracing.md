# 0008 — 키 완전삭제와 남용 추적

**상태**: 채택 (2026-08-12) · **시행**: 2026-08-19 (처리방침 개정 시행일과 같음)
**관련**: #320 · [0001 공유 계약](0001-shared-contracts.md) · [/privacy](../../public/privacy.html) 제3조·제7조 · [/terms](../../public/terms.html) 제3조

## 무엇이 문제였나

오너 제보: *"사용자가 악의적으로 쓰고 키 자체를 폐기해버리면 우리가 추적할 수 없지 않나?"*

코드를 뜯어 보니 **두 동작이 서로 다른 성질**이었고, 문제는 제보가 가리킨 버튼이 아니라 그 옆 버튼이었다.

| 동작 | 하는 일 | 추적 |
|---|---|---|
| 폐기 `DELETE /api/v1/keys` | `UPDATE _keys SET status='revoked'` — **행이 남는다** | key_hash↔email 유지 → **가능** |
| 완전삭제 `?purge=true` | `_keys` 행 **DELETE** | 대응 소멸 → **불가** |

그러니 **폐기는 문제가 아니다.** 유출된 키를 즉시 끄는 유일한 수단이고 상용 서비스도 전부 갖고 있다.

### 진짜 결함 — 상한이 제 구실을 못 했다

재발급 상한(하루 5회)은 오너가 *"무한 재발급 구조 아니냐"* 고 물어 생긴 장치인데(#303),
그 카운터가 `_keys.rotated_day/rotated_count` 에 얹혀 있었다. 완전삭제가 그 행을 지우므로:

```
남용 → 완전삭제 → 재로그인 → 신규 발급(회전이 아니라) → 반복
```

**상한이 막으려던 바로 그 행동으로 상한이 사라졌다.** 남는 제동은 발급 IP 시간당 5회뿐이고 IP 는 바꾸기 쉽다.

여기에 관측 공백이 겹쳤다 — 폐기와 완전삭제가 로그에 똑같이 `route='revoke'` 로 찍혀
**완전삭제가 쓰이고 있는지조차 몰랐다.**

## 왜 "완전삭제를 없앤다"가 답이 아닌가

처리방침 제7조에 **공개 약속**돼 있다. 제6조 ③ 은 *"별도의 승인 절차 없이 즉시"* 까지 못 박았다.
근거 없이 거두면 그게 더 큰 문제다. 화면에서 버튼만 숨기는 것도 답이 아니다 — API 는 열려 있어 **숨긴 척**이 된다.

상용 서비스와의 차이는 **키가 아니라 계정**이다. 저쪽은 키를 지워도 계정이 남아 신원 앵커가 되는데,
우리는 계정이 없고 **이메일 한 줄이 앵커 전부**라 그걸 지우면 앵커가 통째로 사라진다.

## 결정

**① 폐기·완전삭제 둘 다 유지한다.** 삭제권은 그대로다.

**② 재발급 상한을 `_keys` 밖으로 옮긴다** — `_issuance_guard(email_hash, day, count, updated_at)`.
완전삭제는 이 표를 건드리지 않는다. 키 행이 없는데 가드가 있으면 그건 **첫 발급이 아니라 재발급**이므로 상한을 건다.

**③ 보관은 해시 + 30일.** 이메일 원문이 아니라 해시(`sha256("guard|"+SALT+"|"+email)`),
기간은 요청 로그와 같은 30일. 쓸 때마다 오래된 행을 지운다(별도 스케줄러는 안 도는 것을 아무도 모른다).

**④ 폐기와 완전삭제를 로그에서 가른다** — `route` 를 `revoke` / `purge` 로.

**⑤ 남용 시 완전삭제 유예는 하지 않는다** (지금은). 제6조 ③ 을 뒤집는 일이고,
실사용자 남용이 **0건**인 상태에서는 근거가 없다. ④의 관측이 "완전삭제로 상한을 우회한 사례"를 보여줄 때 재검토한다.

## 개인정보 관점

🔑 **정보가 느는 게 아니라 줄어든다.**

| | 종전 | 개정 후 |
|---|---|---|
| 재발급 횟수가 붙는 대상 | 이메일 **원문**(`_keys.email`) | 이메일 **해시** |
| 보유 기간 | 이메일과 같음 = **삭제 요청 시까지(사실상 무기한)** | **30일** |

⚠️ **다만 이 해시는 익명이 아니라 가명이다.** 이메일은 값 공간이 좁아, 비밀값을 아는 서비스는
특정 주소가 이 기록에 해당하는지 대조할 수 있다. 발급 IP 해시에 대해 방침이 이미 쓰고 있는
정직한 서술과 같은 성격이라(제3조), **같은 방식으로 기간을 못 박아** 적었다(제7조 ④).

근거는 **남용 방지라는 정당한 이익**이며, 목적에 필요한 최소 항목·최소 기간으로 한정한다.

## 비용과 대안

| 대안 | 왜 안 골랐나 |
|---|---|
| 완전삭제 제거 | 공개 약속 파기. 화면만 숨기는 변형은 API 가 열려 있어 무의미 |
| 폐기 버튼 제거 | 유출 대응 수단이 사라져 **보안이 나빠진다** |
| 남용 시 삭제 유예 | 제6조 ③ 개정 필요 + 남용 실적 0건 → 근거 부족. ⑤로 보류 |
| 그대로 두기 | 상한이 존재하되 작동하지 않는 상태가 남는다 |

## 🔴 이 결정이 막지 **못하는** 것

과장하지 않기 위해 적는다. 아래 셋은 알고 남기는 구멍이다.

**① 다른 계정을 쓰면 그대로 뚫린다.** 가드는 **이메일 단위**다 — 새 Google 계정을 만들면
새 사람이다. 우리에겐 계정 개념이 없고 이메일 한 줄이 앵커 전부라 여기가 천장이다.
남는 제동은 **발급 IP 시간당 5회**뿐이고 IP 는 바꾸기 쉽다. 이걸 막으려면 신원 확인 층이
필요한데, 그건 이 서비스의 성격(무료·학습용·즉시 발급)과 맞바꿔야 하는 것이라 하지 않는다.

**② 0008 적용 **전**부터 키가 있던 사람은 한 번 공짜다.** 그 계정은 아직 가드 행이 없어서,
첫 완전삭제 뒤 재로그인이 "첫 발급"으로 보인다(기록이 없으니 구분할 방법이 없다).
그 발급이 가드를 만들므로 **두 번째부터는 잡힌다.** 소급 백필은 하지 않는다 — 남은 정보가
없고, 억지로 만들면 그게 새 수집이다.

**③ 하루가 지나면 초기화된다.** 상한이 "하루 5회"라 그렇게 설계된 것이지만,
느긋한 남용(매일 5회)은 이 장치로 막히지 않는다. 그건 ⑤(관측 뒤 재검토)의 영역이다.

⚠️ **`ISSUANCE_SALT` 를 바꾸면 가드가 통째로 고아가 된다**(해시가 달라진다) — 상한이
전원 초기화된다. 같은 값이 state·회전 티켓 서명에도 쓰이므로 그때는 어차피 다른 것도
끊긴다. 비밀값 교체는 그 사실을 알고 해야 한다.

## 롤백

`_issuance_guard` 를 읽지 않게 되돌리면 종전 동작으로 복귀한다(표는 증분이라 남겨 둔다).
`_keys.rotated_*` 컬럼을 **지우지 않은** 이유가 이것이고, 0008 적용 전 계정의 오늘치를 읽는
seed 경로로도 쓴다.

## 시행 순서

처리방침 제10조 ② 가 **"변경 사항의 시행 전에 공개"** 를 약속하므로:

1. 문서(약관·처리방침) 먼저 배포 — 시행일 **2026-08-19** 명시
2. 마이그레이션 `0008` 적용 (빈 표 생성이라 아무것도 수집하지 않는다)
3. **2026-08-19 이후** 동작 변경 배포

🔴 이 순서를 지키지 않으면 두 가지가 일어난다.

1. **고지한 날 이전에 새 항목을 수집**하게 된다(제10조 ② 위반).
2. 🔴 **표가 없으면 발급 경로가 통째로 죽는다.** `readGuard` 의 예외가 그대로 올라가
   Worker 예외(1101)가 된다 — problem+json 도 아니고 원인도 안 보인다(실측으로 확인).

**②를 막는 것은 `npm run deploy:prod` 의 `preflight --require-applied` 다** — 기대 스키마를
`migrations/*.sql` 에서 유도하므로 `_issuance_guard` 가 없으면 **배포를 거부**한다(검증함).
`main` 머지 CD 도 같은 명령을 탄다.

⚠️ **일부러 fail-open 으로 만들지 않았다.** 표가 없을 때 조용히 옛 동작(= 우회 가능)으로
돌아가면, 그건 **이 이슈가 고치려던 바로 그 병**이다 — 보호 장치가 있는 척하면서 안 도는 것.
게이트가 막는 상태를 위해 코드에 예외 처리를 더하는 대신, **크게 실패하고 배포를 막는 쪽**을 골랐다.
