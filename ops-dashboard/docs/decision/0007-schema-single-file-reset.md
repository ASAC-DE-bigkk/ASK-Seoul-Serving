# 0007 — _ops_* 마이그레이션은 증분(추가만) — 리셋 규약 폐지

- 상태: **개정** (2026-08) — 처음(2026-07)에는 "단일 파일 DROP+CREATE 리셋"이었다
- 관련: ASK-Seoul#78 **D-6**(선행 필수: 대시보드 마이그레이션 증분 전환, 적용 순서 **0단계**),
  [reference/](../reference/) 의 "D1 Migration 정책(증분·하위 호환)" 항목

## 맥락

처음에는 `migrations/0001` 하나가 정본이고 컬럼이 늘면 DROP+CREATE 로 통째 다시 만들었다.
내용물을 로더·픽스처가 매번 다시 채워 "잃을 상태가 없다"는 전제였다.

그 전제가 깨졌다. 팀 규약(#78)이 조회 DB 를 공유 자산으로 만들었고, ASAC-DAG 적재기가
**실제 팀 D1 에 `_ops_*` 가족 테이블을 만들어 데이터를 쌓기 시작했다.** 규약 D-6 은 이 사고를
정확히 지목한다 — *"대시보드 마이그레이션이 DROP TABLE IF EXISTS 로 시작한다. 팀 조회 DB 에
테이블을 만들기 전에 증분 방식으로 바꿔야 한다. 안 바꾸면 첫 스키마 수정이 팀 데이터를 지운다."*
같은 이유로 정본 모듈(`d1_ops.py`)은 DROP 문 자체를 만들지 않는다.

## 결정

- **마이그레이션 파일은 DROP 을 포함하지 않는다.** `CREATE TABLE IF NOT EXISTS` +
  이후 변경은 **ALTER 추가 파일**(0003, 0004 …)로만 — 항목 추가는 허용, 삭제·이름 변경은
  금지(D-3)다.
- 내용물 리프레시는 마이그레이션이 아니라 **픽스처·로더의 몫**이다 — 이미 그렇게 돼 있다
  (`slo_sample.sql`·`slo_live.sql` 모두 자기 범위를 DELETE 하고 다시 넣는다).
- 로컬에서 스키마를 통째로 리셋하고 싶으면 마이그레이션에 DROP 을 넣는 게 아니라
  **로컬 상태를 지운다**: `rm -rf ../marketplace/.wrangler/state` 후 양쪽 재시드.

## 대가

- 프로토타입인데도 컬럼 변경마다 ALTER 파일이 는다 — 팀 데이터를 지킬 수 있다면 싼 값이다.

## 재검토 조건

없음 — 팀 D1 에 실데이터가 있는 한 되돌릴 수 없는 방향이다. 예외적으로 로컬 전용
테이블을 새로 만드는 경우에도 같은 규약을 따른다(습관이 사고를 막는다).
