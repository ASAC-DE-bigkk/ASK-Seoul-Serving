# 0006 — 키 조치 식별자는 key_hash, 상태는 두 개

- 상태: **채택** (2026-07)
- 관련: [reference/](../reference/) 의 "API Key 상태 모델(PENDING…EXPIRED)" 항목

## 맥락

화면에 보이는 키 식별자는 `key_prefix`(`ask_`+4hex, 8자)다. 사람 눈에는 충분하지만
**충돌할 수 있고**, 엉뚱한 사람의 키를 폐기하는 사고는 되돌리기 어렵다.

## 결정

- **모든 조치(`POST /api/keys`)는 `key_hash`(64hex)로 받는다.** 형식 검증(`^[0-9a-f]{64}$`)
  후 존재 확인, 응답에는 `key_prefix` 를 돌려줘 사람이 확인할 수 있게 한다.
- 해시는 자격증명이 아니다 — 인증에는 원문이 필요하므로 해시를 알아도 호출할 수 없다.
  그래서 응답·화면에 실어도 된다.
- 게이트웨이의 셀프 폐기(`DELETE /api/keys`, 원문 필요)와 달리 **키 원문 없이** 조치한다 —
  이용자가 키를 잃어버려도 운영자는 조치할 수 있어야 한다.
- 키 상태는 게이트웨이 정본 규약 그대로 **`active` / `revoked` 두 개**다. reference 의
  5-상태 모델(PENDING/ACTIVE/SUSPENDED/REVOKED/EXPIRED)은 채택하지 않았다 —
  발급 즉시 활성이고 만료·승인 대기가 없는 현 게이트웨이에 세 상태는 죽은 코드다.
- `delete` 는 이용자의 삭제 요청을 운영자가 대신 처리하는 경로다. `_usage`·`_burst`·`_keys`
  를 함께 지운다. `_request_log` 의 `key_hash` 는 남지만 해시→이메일 대응이 사라져
  사람과 연결되지 않는다(처리방침 그대로).

## 재검토 조건

게이트웨이가 상태 모델을 넓힐 때(만료, 승인 대기 등) — 정본이 저쪽이므로 **게이트웨이와
공동으로** 개정한다.
