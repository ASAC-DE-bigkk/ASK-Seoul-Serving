# 변경 이력

> **왜 이 문서가 있나** — 커밋 메시지는 *무엇을 바꿨나*를 적지만 **왜 그렇게 하기로 했나**는
> 이슈·PR 코멘트에 흩어진다. 시간이 지나면 "이건 왜 이 모양이지"에 답할 곳이 없어져
> 같은 논의가 다시 열리고, 이미 폐기한 안을 다시 시도하게 된다.
>
> **결정의 정본은 [`agreement.md`](agreement.md)** 이고, 이 문서는 **그 결정이 언제 무슨
> 의도로 코드에 닿았는지**를 시간순으로 남긴다. 둘은 역할이 다르다 —
> 저쪽은 "지금 무엇이 정해져 있나", 여기는 "어떤 순서로 어떻게 왔나".

## ⚠️ 이 문서 이전의 작업

**이 문서는 2026-08-04 에 처음 만들었다.** 그 전의 작업도 아래에 소급해서 적었지만,
**기록을 남기며 진행한 것이 아니라 뒤늦게 복원한 것**이다. 그래서:

- **실제로는 이뤄졌으나 여기 없는 작업이 있을 수 있다.** 특히 이 리포로 이관되기 전
  (`ask-seoul` 인프라 리포의 `serving-gateway/`·`ops-console/` 시절)과, 초기 며칠 사이의
  작은 변경들이 그렇다.
- 소급분의 **날짜는 커밋·이슈 시각 기준**이고, 그날 실제로 오간 논의 전부는 아니다.
- 빠진 것을 발견하면 **지우지 말고 추가**한다. 뒤늦게라도 남는 편이 낫다.

**2026-08-04 이후 항목은 작업과 함께 적는다** — 나중에 몰아 쓰면 의도가 이미 흐려져 있다.

### 서빙 로그에도 환경 스코프 — 배포되면 local·prod 가 섞일 자리였다 (#64)

- **작업자**: @Exisign
- **의도 · 목표**: 콘솔이 `_gateway_request_log.env` 를 **필수 컬럼으로 요구해 놓고 어느
  질의에서도 안 쓰고 있었다.** 게이트웨이가 미배포라 전 행이 `local` 이어서 표가 안 났을
  뿐, 배포되는 순간 `local` 과 `prod` 가 한 화면에 합산된다. **파이프라인이 이미 겪은
  함정**을 서빙 쪽에서 그대로 반복할 자리였다(#52 §11 C-4 · ASAC-DAG#654).
- **조치**
  - `envScope(env)` · `gwWhere(env)` 를 모듈 층에 두고 **서빙 로그 전 질의에 적용**했다 —
    summary(서빙·이용행동) · keys · usage(API 사용량) · usageDetail. 파이프라인의 `evWhere`
    와 같은 규약이다. summary 안에 있던 지역 `SCOPES` 도 이 상수를 쓰게 합쳤다(두 벌이면 갈린다).
  - **좁히는 건 운영 화면(`ENV_SCOPE`)뿐이다.** 개발 화면은 좁히지 않는다 — "섞였다"는
    사실 자체가 이 콘솔이 드러내야 할 관측이다. 대신 **섞인 채로 보고 있다는 것**을 알린다.
  - 🔴 **`env IS NULL` 을 운영으로 채우지 않는다.** 없는 정보를 운영이라 단정하면 로컬
    요청이 운영으로 보인다(ASAC-DAG#692 와 같은 기준). `(미상)` 으로 따로 세어 화면이 말한다.
  - **`/api/trace` 만 예외로 거르지 않는다.** `request_id` 는 지원 문의의 출발점이라, 다른
    환경 요청이어도 "그 환경 것이다"라고 답하는 편이 "없다"보다 낫다 — 대신 `env` 를 같이 실었다.
- **결과** — 게이트웨이를 `ASK_ENV=prod` 로 한 벌 더 띄워 **실제로 섞어 놓고** 확인:
  - 운영 스코프(`ENV_SCOPE=prod`): 전체 141건 중 **prod 18건만** 셈. `local 123건`을 뺐다고
    네 탭이 말함. 요청 종류 합(6+3+3+3+2+1=18)과 일자별 합(인증 7 + 익명 11)이 맞음
  - 개발 화면: **좁히지 않고 141건 전부**, 대신 "▲환경이 섞여 있음 — local 123 · prod 18" 경고
  - JS 오류 0
- **남은 것**: 검증용으로 로컬 D1 에 `env='prod'` 18건이 실제로 쌓였다. 게이트웨이가 낸
  진짜 행이고 30일 뒤 sweep 으로 빠진다. 당장 지우려면
  `wrangler d1 execute ask-seoul-dev-d1 --local --persist-to ../marketplace/.wrangler/state
  --command "DELETE FROM _gateway_request_log WHERE env='prod'"`.

### 콘솔이 route 5종만 알던 것 — 게이트웨이 실체 12종과 맞춤 (#63)

- **작업자**: @Exisign
- **의도 · 목표**: @yooseongjin527 이 `dev` 기준으로 네 표면과 콘솔을 대조해 올린 지적.
  `/skill/v1` 과 `/mcp` 가 붙으면서 **콘솔이 아는 route 는 5종인데 게이트웨이가 내는 값은
  12종**이 됐다. 세 곳에서 어긋났다 — 화면 문구 · 집계 · 제품 축.
- **조치**
  - **① 내부 슬러그가 화면에 새던 것** — `ROUTE_KO` 를 12종 전수로. `skill_data`·`mcp`·
    `v1_product` 가 그대로 찍히던 자리가 "스킬 데이터 조회"·"AI 연결(MCP)"·"제품 번들"이 됐다.
  - **② `route='data'` 하드코딩 5곳** — 제품별 수요 · 키 활성화 판정(2곳) · 에이전트별
    데이터 호출 · API 사용량. **조건을 다섯 군데 흩어 둔 것이 원인**이라 `SERVE` 상수
    한 줄로 모았다. 새 문이 생기면 거기만 고친다.
  - **③ 제품 축이 `table_name`** — `PRODUCT_KEY = COALESCE(product_id, table_name)` 로 옮겼다.
    `0005` 이전 행은 `product_id` 가 NULL 이라 표명 폴백이 필요하다. `_catalog` 조인도 같은
    우선순위로 바꿨다 — OR 로 묶으면 한 행이 두 제품에 붙는다.
  - **④ `route='page'` 로 걸러 영원히 비던 카드** — 게이트웨이 라우터에 그런 값이 없다.
    조건이 아니라 오타에 가까웠다. 조건을 걷어내고, 대신 **축이 실제로 채워졌는지**를
    창 안에서 세어(`fill`) 카드가 **"게이트웨이 미발행"** 을 근거 있게 말하게 했다.
    `ua_class`·`agent_name`·`page_path` 도 같은 처지였고 전부 "데이터 없음"이라 거짓말하고 있었다.
- **결정하지 않고 남긴 것**: **MCP 는 데이터 서빙 집계에서 뺐다.** `route='mcp'` 한 값이라
  `query_product`(데이터)와 `list_products`(목록)가 갈리지 않는다(#62 는 상태만 고쳤다).
  넣으면 부풀고 빼면 모자라므로, **빼고 뺀 건수를 화면이 말한다** — 세 탭에 "MCP 는 못 가름"
  칩. 침묵하면 "MCP 는 안 쓰인다"로 읽히고 그건 관측 공백을 이상 없음으로 위장하는 것이다.
- **결과** — 네 표면(api·skill·v1·mcp)을 실제로 태워 확인:
  - 요청 종류별에 10종이 **전부 한글로** — 내부 슬러그 0개
  - 제품별 수요 축이 `commerce_age_band`(product_id), 표명 `d1_age_band` 는 폴백 표기
  - `skill_data` 가 "실제 조회"에 잡힘 — 전환 배수가 1.0 → 1.8배로 정정됨
  - `meta.serve_routes=["data","skill_data"]` · `mcp_calls=16`(뺀 건수) · `axes_unfilled` 4종
  - JS 오류 0
- **뒤늦게 하나 더**: 제품 **상세**도 `table_name` 으로 찾고 있었다. 목록만 `product_id` 로
  옮기고 상세를 두면, `table_name` 이 비고 `product_id` 만 있는 행(스킬·MCP)이 상세에서만
  사라져 **목록과 상세의 숫자가 어긋난다.** 두 이름을 다 받게 고쳤다.
- **되짚을 것**: 같은 **TDZ 실수를 두 번** 했다 — 서버는 `fill` 구조분해 앞에서 `F` 를 썼고
  (`/api/summary` 전체가 500), 화면은 `apiName` 을 첫 사용처보다 뒤에 뒀다(render 전체 사망).
  **`node --check` 는 둘 다 통과시킨다.** 띄워서 실제로 눌러 보는 검증이 없으면 못 잡는다.
  덧붙여 스크린샷 도구가 포트를 안 받아 **고친 화면 대신 옛 화면을 찍고 "안 고쳐졌다"고
  읽을 뻔했다** — `shot.mjs` 에 대상 URL 인자를 붙였다.

  둘 다 정상인데 화면이 "데이터 없음"만 띄우니 **"콘솔이 고장났나"로 읽혔다.**

  - `ok` 인데 0행이고 원격 소유 → **"로컬은 비어 있음"** — 흔한 오해라 따로 짚는다
  - 같은 이유의 칩은 **탭당 하나로 합치고** 표 이름을 나열한다(표마다 내면 시끄럽다)
  - 한 표가 여러 탭을 먹이는 것도 반영(`_gateway_request_log` → 응답 상태·이용 행동·API 사용량)
- **결과**
  - 로컬: `pipeline` "이 환경에 없음"(발행 대장 2종) · `runs` "로컬은 비어 있음"(조회 DB 4종)
  - 운영: `serving`·`usage`·`apis`·`keys` 가 각각 "이 환경에 없음"으로 이유를 말함
  - **비는 것 자체는 안 고쳤다** — 고칠 수 있는 게 아니다. 운영에서 게이트웨이 표가 생기는
    것은 **P-3(원격 apply)** 이후이고, 그때 한 화면에서 전부 보인다.
  - 지금 전체를 보려면 두 환경을 오가야 한다: 파이프라인은 `npm run dev:prod-readonly`,
    게이트웨이는 `npm run dev`. 이 사실을 화면이 직접 말한다.

  — `--ack` 는 판정을 바꾸지 않고 사유를 함께 찍는다.

    표 89개를 한 문장에 물으면 길이 한도에 걸리는 것(ASAC-DAG#677 과 같은 함정).

### 요청 로그 표 개명 — `_request_log` → `_gateway_request_log`

- **작업자**: @yooseongjin527 (PR #53) · 결정은 #44 전원 확인
- **의도 · 목표**: 운영·개발 D1 에 게이트웨이 정본과 **다른 스키마**의 `_request_log` 가 이미

    좌우된다"* 가 가정이 아니라 **일어난 일**이었고, 그게 개명의 결정적 근거가 됐다.
