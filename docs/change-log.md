# 변경 이력

> **왜 이 문서가 있나** — 커밋 메시지는 *무엇을 바꿨나*를 적지만 **왜 그렇게 하기로 했나**는
> 이슈·PR 코멘트에 흩어진다. 시간이 지나면 "이건 왜 이 모양이지"에 답할 곳이 없어져
> 같은 논의가 다시 열리고, 이미 폐기한 안을 다시 시도하게 된다.
>
> **결정의 정본은 [`agreement.md`](agreement.md)** 이고, 이 문서는 **그 결정이 언제 무슨
> 의도로 코드에 닿았는지**를 시간순으로 남긴다. 둘은 역할이 다르다 —
> 저쪽은 "지금 무엇이 정해져 있나", 여기는 "어떤 순서로 어떻게 왔나".

## ⚠️ 이 문서 이전의 작업

**이 문서는 2026-08-04 에 처음 만들었다.** 그 전의 작업도 아래에 소급해서 적었지만,
**기록을 남기며 진행한 것이 아니라 뒤늦게 복원한 것**이다. 그래서:

- **실제로는 이뤄졌으나 여기 없는 작업이 있을 수 있다.** 특히 이 리포로 이관되기 전

**2026-08-04 이후 항목은 작업과 함께 적는다** — 나중에 몰아 쓰면 의도가 이미 흐려져 있다.

### '응답 상태' 탭 전체에 분야 축을 싣는다 — "축이 없다"는 서술이 틀렸다 (#156)

- **작업자**: @Exisign
- **의도 · 목표**: '보는 분야'를 바꿔도 `#daily`(날짜별 요청 건수)가 그대로라는 제보에서
  출발해 탭 전체를 훑었다. **여섯 카드 중 셋만 좁혀지고 있었다.**
- **원인 — 축이 없던 게 아니라 안 실었던 것이다.**
  화면은 *"요청 종류·날짜별 요청·이용자 재방문은 분야 축이 없는 지표"* 라고 적고 있었는데
  **사실이 아니다.** `_gateway_request_log` 에 `product_id` 가 있으니 축은 처음부터 있었고,
  서버 질의가 `GROUP BY` 에 안 넣었을 뿐이다. 화면이 자기 한계를 잘못 설명하고 있었다.
- **더 나빴던 것 — 실패 목록은 거르는 시늉만 했다.**
  화면이 `table_name` 접두사로 분야를 뽑았는데 그건 **등급**이다:
  `gold_transit_parking_full_risk` 의 앞부분은 'transit' 이 아니라 **'gold'** 라
  어느 분야를 골라도 안 걸렸다. 게다가 `table_name` 이 NULL 인 행이 최다인데(실측 43건 —
  표를 못 찾은 4xx) 그건 조용히 사라졌다. #63 이 이미 "표명 접두사는 가짜 분야를 만든다"고
  적어 뒀는데, 그 교훈이 서빙 탭 필터에는 적용돼 있지 않았다.
- **또 하나 — 상위 N 을 뽑아 놓고 걸렀다.** 제품·실패·0건 목록은 전체 상위 N 을 받아
  화면에서 분야로 거르는 구조라, **상위 N 밖의 분야는 0건으로 보였다.** 있는 것을 없다고
  말하는 쪽이라 그냥 잘리는 것보다 나쁘다.
- **조치**
  - 서버에 `GW_DOM` 신설 — 분야는 **`product_id` 접두사 하나만** 인정한다. 접두사가 없는
    값(`seoul-urban-analytics` 등 실측 39건)과 제품 없는 요청은 `null` = **분야 미상**이고,
    아무 분야에도 안 끼운다.
  - `daily`·`routes`·`failures`·`products`·`empty`·`keys` 전부에 `domain` 을 싣는다.
  - `topPerDomain()` 신설 — 상위 N 을 **분야마다** 뽑는다(`ROW_NUMBER() OVER PARTITION BY`).
    전체 상위 N 은 분야별 상위 N 의 부분집합이라(정렬 기준이 같다) 결과 하나로 두 화면을
    정확히 그린다. 행 수는 (분야 수+1)×N 로 묶인다.
  - `serving.totals` 신설 — KPI 전용 합계(분야별 + `'*'` 전체). **목록을 더해 만들지 않는다:**
    목록은 상위 N 이라 합이 전체가 아니고, `COUNT(DISTINCT key_hash)` 는 분야별 값을 더할
    수도 없다. 실제로 '사용 중인 이용자'가 `keys` 목록 길이를 세는 바람에 **10에서 멈춰
    있었고**, '전체 요청'(전체값)과 '결과 0건'(분야값)이 한 줄에 섞여 있었다.
  - `daily` 의 `keys_used`(DISTINCT)를 빼고 `errors` 를 넣는다 — 화면이 `x.errors` 를 읽는데
    질의에 없어서 **막대 툴팁의 실패 수가 한 번도 안 떴다.** `keys_used` 는 아무도 안 읽었다.
  - 화면: `servRows`·`servStar`·`servTotal`·`mergeRows` 로 버킷을 고른다. 평균 응답시간은
    **건수로 가중**해 합친다(평균의 평균을 내면 적게 불린 쪽이 과대 대표된다).
  - 스코프 배너를 사실대로 고쳤다 — "이 화면 전부를 좁혔다" + **분야 미상 건수를 밝힌다**.
    "분야별을 다 더해도 전체보다 작다"를 화면이 직접 말한다(0012).

### 자동 새로고침이 보던 탭에서 사람을 끌어내던 것을 멈춘다 (#153)

- **작업자**: @Exisign
- **의도 · 목표**: '이용자 키' 탭을 보고 있으면 30초 자동 새로고침 때 **'API 사용량' 탭으로
  강제 전환**됐다. 자동 새로고침의 존재 이유가 "보던 자리를 지키며 값만 갱신"인데
  (`load()` 가 스크롤 위치까지 되돌려 놓는다) 탭 자체가 바뀌면 그 전제가 무너진다.
- **원인** — 주소와 화면이 어긋나는 자리가 **하나** 있었다.
  `render()` 가 끝에서 `showTab(parseHash().pane)` 으로 **주소에서 탭을 다시 골랐다.**
  대부분의 탭은 `showTab` 이 주소를 같이 갱신하니 값이 같아 표가 안 났는데,
  **키 탭만 주소를 안 쓴다** — 조건을 `syncKeyHash()` 가 관리하므로 `showTab` 이 early
  return 한다(주소로 들어온 링크의 필터를 덮어쓰지 않으려고 일부러 그렇게 뒀다).
  그래서 키 탭을 **클릭으로** 열면 주소가 이전 탭(`#apis` 등)에 머물렀고, 다음 갱신이
  그 주소대로 사람을 옮겼다. 딥링크(`#keys?…`)로 들어오면 주소가 맞아 안 났다 —
  **클릭으로 연 경우에만** 나서 재현 조건이 헷갈렸다.
- **조치**
  - `activePane()` 신설 — 열린 탭은 `aria-selected` 가 정본이다. `render()` 는
    **지금 열린 탭을 다시 적용할 뿐**이고, `showTab` 을 부르는 목적은 이동이 아니라
    **알림 칩 가시성**(배너를 render 가 새로 만들므로 자기 탭 것만 남기는 처리)이다.
  - 딥링크 반영을 **부트 1회**로 옮겼다(`hashchange` 는 최초 진입에 안 뜬다).
    최초 1회와 매 갱신을 갈라 두니 겸업에서 오던 부작용이 사라진다.
  - 사람이 탭을 고를 때(클릭·화살표)는 키 탭도 주소를 맞춘다(`gotoTab`).
    🔴 **`showTab` 안에서 하면 안 된다** — `hashchange` 경로에서 `applyKeyHash` 보다
    먼저 돌아 옛 `KEYQ` 를 주소에 써 버리고, 그러면 필터를 걸고 넘어온 링크가 즉시
    '전체'로 되돌아간다(원래 early return 이 막고 있던 그 사고다).
- **곁가지로 드러난 것** — `#<탭>?dom=<분야>` **공유 링크의 스코프가 원래부터 안 걸렸다.**
  `showTab` 이 현재 `DOMSCOPE`(빈 값)로 주소를 다시 써서 `?dom=` 을 지운 **뒤에**
  `load()` 가 읽고 있었다. dev 원본과 대조해 **이번 변경과 무관한 기존 결함**임을 확인했다.
  부트에서 `showTab` 보다 **먼저** `DOMSCOPE` 를 세워 고쳤다(중복 render 도 하나 준다).
- **결과** — jsdom 으로 실제 클릭·갱신·딥링크를 돌려 **26개 단언 전부 통과**.
  키 탭 클릭 후 갱신 유지 · 나머지 네 탭도 유지 · `#keys?filter=` 필터 보존 ·
  `#apis/<이름>` 상세와 주소 유지 · `#serving?dom=culture` 스코프 반영 ·
  주소로 옮기는 경로(hashchange)도 그대로 · 스크립트 오류 0.
  앞선 표시명·등록부 작업도 회귀 없음을 같은 방식으로 확인했다.

### 운영 전환 — Google 발급을 켰다 (#110 ② 완결)

- **작업자**: @yooseongjin527
- **의도 · 목표**: 코드는 배포됐지만 `GOOGLE_CLIENT_SECRET` 이 없어 **꺼진 채** 돌고 있었다.
  시크릿을 넣어 정책을 전환하고, 운영에서 실제 로그인까지 끝냈다.
- **조치 · 실측**
  - `main` 머지 → CD(`deploy-prod.yml`) 자동 배포. `sha=80fc631` · gateway·console 둘 다 성공.
  - `wrangler secret put GOOGLE_CLIENT_SECRET --env production`. 🔑 **이 명령이 워커를 새
    버전으로 올려 코드 재배포 없이 즉시 반영된다.**

    ```
    key_issuance              google_oauth   ← 즉시 뒤집혔다
    POST /api/v1/keys         403
    GET  /api/v1/auth/google  302  redirect_uri=https://ask-seoul.kr/…/callback
    auth_start 302 → auth_callback 201 (585ms)   운영에서 실제 키 발급 완료
    ```
  - **캐시 키 수정(앞 항목)이 실전에서 증명됐다** — 시크릿을 넣자마자 `key_issuance` 가
    뒤집혔다. 그 수정이 없었으면 **최대 10분간 화면이 이메일 폼을 띄우고 제출은 403** 을
    받는 구간이 생겼다.
  - 시크릿 넣기 전의 `auth_callback 503` 이 로그에 남아 있다 — **fail-closed 가 제대로
    동작했다는 증거**다.
- **결과**
  - `_keys` 에 **소유가 확인된 첫 키**(`ask_a199`)가 생겼다. 옛 키(`ask_6507`, 이메일 폼으로
    받은 것)는 그대로 유효하다 — 발급 경로만 닫혔지 기존 키를 무효화하지는 않는다.
  - ⚠️ **동의 화면 게시 상태는 미확인**이다. "테스트" 면 등록된 100명만 로그인된다 —
    외부 공개가 목적이면 프로덕션 게시가 필요하다.
  - 🔎 검증 중 **두 번 오진했다** — ① `key_issuance` 가 없다고 봤는데 `grep` 패턴이 `": {"`
    공백을 못 맞춘 것이었다 ② `docs.html` 이 미반영이라고 봤는데 `/docs.html` → `/docs`
    **307 리다이렉트를 안 따라간 것**이었다(`curl -L` 없이). `git show origin/main` 도

    틀린 것**이었다 — 검증 명령을 먼저 의심해야 했다.

### Google 발급 실물 검증 — 그 과정에서 캐시 버그를 잡았다 (#110 ② 후속)

- **작업자**: @yooseongjin527
- **의도 · 목표**: 앞 항목이 *"실제 로그인 왕복은 미검증"* 으로 끝나 있었다. OAuth 클라이언트를
  만들고 **로컬에서 Google 과 실제로 주고받아** 그 구멍을 메웠다.
- **조치 · 실측**
  - `.dev.vars` 에 `GOOGLE_CLIENT_ID`·`GOOGLE_CLIENT_SECRET` 을 넣고 로컬 구동. 브라우저로
    실제 Google 로그인을 **두 번** 돌려 두 분기를 다 봤다.

    ```
    auth_start     302   리다이렉트 · scope=openid email · 서명된 state · prompt=select_account
    auth_callback  201   새 계정 → 키 발급 (4,979ms)
    auth_callback  409   기존 계정 → 중복 차단, 회전하지 않음 (1,526ms)
    POST /api/v1/keys 403  이메일 발급이 닫혔다
    ```
  - **`route` 값이 로그에 그대로 찍혔다** — `auth_start`·`auth_callback`. 0014 계약대로다.
  - 곁들여 **`agent_verified` 가 브라우저 요청에서 NULL** 로 찍혔다 — #111 의 3분기가 실물에서
    맞다는 확인이다(0 이 아니라 NULL: 브라우저는 검증 대상이 아니다).
  - 🐛 **찾아 고친 버그 — 캐시가 정책 전환을 최대 10분 늦춘다.** `key_issuance` 가 **캐시된
    카탈로그 본문 안에** 있는데 캐시 키에는 발급 방식이 안 섞여 있었다. 정책을 켠 직후에도
    캐시가 `"email"` 을 주고, 그 사이 화면은 이메일 폼을 띄우며 제출은 403 을 받는다.
    **엣지 캐시는 배포를 넘어 살아남으므로 prod 에서 그대로 재현될 문제였다.**
    캐시를 지우는 대신 **키를 갈랐다** — `?ki=google_oauth|email`. 정책이 바뀌면 다른 칸을
    보므로 즉시 새 값이 나가고 옛 칸은 TTL 로 만료된다. **로컬에서 안 돌려 봤으면 못 찾았다.**
  - `src/mcp.js` 의 인증 실패 안내가 `POST /api/v1/keys` 를 가리키고 있었다 — prod 에서 403 이
    될 문이다. `key_issuance` 를 보게 고치고, **MCP 클라이언트는 브라우저를 못 여니 사람이
    받아 설정에 넣는다**는 것까지 문구에 넣었다(안 적으면 에이전트가 로그인 URL 을 열려 든다).
- **결과**
  - PR #121 의 **"실제 로그인 왕복 미검증"이 해소**됐다.
  - ⚠️ **검증이 운영 `_keys` 에 키 2개를 만들었고 정리했다**(`_usage`·`_burst` 는 0행 —
    발급만 되고 안 쓰였다). 하나는 로그인이 만든 것이고, **하나는 내 실수**다: OAuth 가 켜지기
    **전에** 403 을 확인하려고 발급 엔드포인트를 두드려 201 로 진짜 키가 났다.
    **이 확인은 정책이 켜진 뒤에만 한다.**
  - ⚠️ **캐시 키 수정이 기존 테스트 2건을 깨뜨렸다**(내 회귀). 테스트가 캐시 키를

### 발급 이메일 소유 확인을 Google 에 위임한다 (#110 ② · #20 외부 공개 결정의 하류)

- **작업자**: @yooseongjin527
- **의도 · 목표**: 발급 폼이 받던 주소는 **아무나 적을 수 있었다**(#110). 형식 검증(#109)을
  아무리 조여도 이건 못 막는다 — `qe@gg.gg` 는 형식상 정상이고 남의 주소도 통과한다.
  #20 이 **외부 공개**로 정해지면서 #110 의 트리거가 충족돼 착수했다.
  확인 메일(#110 ①) 대신 **Google 이 이미 확인한 값을 받아 오는** 쪽을 택했다.
- **조치**
  - `src/google-oauth.js` 신설 — state 서명·ID 토큰 판정 같은 **순수 로직만**. 네트워크·D1 을
    안 타서 단독 테스트가 붙는다(`scripts/google-oauth.test.mjs`, 16 test).
  - 라우트 둘: `GET /api/v1/auth/google`(302) · `GET /api/v1/auth/google/callback`.
  - 🔑 **ID 토큰 서명을 검증하지 않는다.** `client_secret` 을 내고 **토큰 엔드포인트에서 TLS 로
    직접** 받은 토큰이라 중간자가 없다(OIDC Core §3.1.3.7). **JWKS 수신·캐시·회전 대응 층이
    통째로 필요 없어진다.** 대신 이 전제가 좁다는 것을 함수 이름
    (`readIdTokenFromTokenEndpoint`)과 주석에 못 박았다 — 클라이언트가 보낸 토큰에 쓰면 안 된다.
  - 검사는 `iss` · `aud` · `exp` · **`email_verified === true`**. 마지막 하나가 이 이슈의 전부다.
  - CSRF state 는 **서명된 단명 쿠키**(HttpOnly · SameSite=Lax · https 일 때만 Secure).
    D1 표를 안 만든다 — 상태를 서버에 두면 청소 주기·경합을 같이 안게 되고 이 용도엔 과하다.
    서명 키는 `ISSUANCE_SALT` 재사용(배포마다 이미 있고, 없으면 발급이 이미 닫힌다).
  - 🔴 **키를 URL 에 싣지 않는다.** 리다이렉트로 넘기면 주소창·이력·Referer·로그에 남는다.
    콜백이 **직접 HTML 을 그려** 한 번만 보여준다 — 기존 "지금 한 번만 표시" 계약 그대로이고
    새 엔드포인트도 새 표도 없다.
  - **이미 키가 있으면 회전하지 않는다.** 콜백의 `code` 는 일회용이라 "정말 만료시킬까요"를
    되물을 왕복을 만들 수 없고, 파괴적 동작을 무확인 실행하지 않는다. 기존 `key_prefix` 를
    보여주고 폐기 경로를 안내한다.
  - **`GOOGLE_CLIENT_ID` 가 채워지면 `POST /api/v1/keys` 가 403 으로 닫힌다.** 두 문을 열어
    두면 느슨한 쪽으로만 온다. 미설정(로컬·테스트)에서는 그대로 동작 — **설정 여부가 곧 정책**이다.
  - `/api/v1/catalog` 에 `key_issuance` 추가 — 화면을 안 거치는 소비자도 키 받는 법을 알아야
    하고, 환경마다 갈리므로 문서가 아니라 응답이 말한다. 카탈로그 화면이 이 값으로 이메일칸과
    Google 버튼 중 **하나만** 띄운다(둘 다 띄우면 닫힌 문을 먼저 두드린다).

### 발급 화면의 이메일 검증을 켠다 — `type="email"` 이 한 번도 안 돌고 있었다 (#109 잔여)

- **작업자**: @yooseongjin527
- **의도 · 목표**: 서버 정규화(같은 날 앞 항목)로 실질 방어는 섰지만, **화면은 여전히 아무
  문자열이나 그대로 보내고 있었다.** 입력칸이 `<form>` 밖이고 발급이 `click` 핸들러에서
  곧바로 `fetch` 하는데, HTML 제약 검증은 **submit 이나 `checkValidity()` 에서만** 돈다.
  즉 `type="email"` 이 붙어 있어도 **키보드 힌트 역할만** 하고 있었다.
- **조치**
  - 발급 핸들러에서 `reportValidity()` 를 부른다. **그 전에 서버와 같은 정규화**(trim +
    후행 점 제거)를 한 번 한다 — 순서를 뒤집으면 서버가 합쳐서 받아 줄 `qe@gg.gg.` 를
    화면이 먼저 거절해 판정이 갈린다.
  - 입력칸에 `required` + `pattern="[^@\s]+@[^@\s]+\.[^@\s]+"` + `title`.
    🔑 **`pattern` 은 점 요구 하나만 더한다** — HTML5 의 도메인 규칙(레이블이 영숫자로
    시작·끝)은 서버 `normalizeEmail` 과 **이미 같고**(서버 쪽을 HTML5 에 맞춰 뒀다),
    다른 건 HTML5 가 점을 안 요구한다는 것뿐이다. 규칙 전체를 복제하면 두 곳이 갈린다.
  - `friendly()` 에 `invalid email` 분기 추가 — 화면 검증을 통과해도 서버가 더 좁게 볼 수
    있고, API 직접 호출자도 이 문구를 본다.
- **결과**
  - **화면 판정이 서버와 12/12 일치**(로컬 실측). 앞 항목에서 남겨 뒀던 어긋남 두 줄이 닫혔다.

    ```
    qe@gg.gg.   →  정규화 qe@gg.gg  →  화면 ✅ / 서버 ✅   (전에는 화면만 ❌)
    qe@gg       →                      화면 ❌ / 서버 ❌   (전에는 화면만 ✅ → 왕복 400)
    ```
  - **잘못된 입력이면 요청이 아예 안 나간다** — `qe@gg` · `qe@gg..gg` · 빈 값으로 발급을
    눌렀을 때 `/api/v1/keys` 호출 **0건**(fetch 계측).
  - `npm test` 139 PASS · 0 FAIL (이 변경은 화면이라 테스트 증가 없음, 회귀 없음 확인).
  - ⚠️ 브라우저 패널이 화면에 없어 **네이티브 검증 말풍선 스크린샷은 못 남겼다.** 기능은
    위 두 실측으로 확인.

  재결정"으로 미뤄 둔 상태**였다 — 로컬 `cf` 가 더미라 실측이 불가능했기 때문이다.
  `ask-seoul.kr` 이 배포되면서 **그 조건이 충족됐다.**
- **조치**
  - **실측이 먼저였다.** `wrangler tail --env production --format json` 으로 **코드 변경도
    배포도 없이** 배포본의 `request.cf` 를 받았다(읽기 전용). 결과: **`verifiedBotCategory`

    ```
    AI 에이전트 + 카테고리 있음  →  1     CF 가 확인했다
    AI 에이전트 + ""             →  0     자칭인데 CF 가 확인 못 했다 = 진짜 검증 실패
    AI 에이전트가 아님            →  NULL  검증할 것이 없다
    ```

    대상이 아니다(§3-1 · #78 F-3). 필드 자체가 없을 때도 NULL 이다: **"봤는데 아니다"(`""`)와
    "못 물어봤다"(부재)는 다른 사실**이고, 후자를 0 으로 적으면 모른다가 검증 실패로 굳는다.
  - `LOG_COLUMNS`·`logValues`·`trace` 에 배선. `logValues` 는 **`??` 를 쓴다** — `||` 였으면
    0 이 조용히 NULL 로 바뀌어 "검증 실패"가 "검증 안 함"이 된다.
  - `index.js` 의 '아직 채우지 않는 셋' 주석을 **둘**로(`page_path`·`pattern_id`).
- **결과**

### ua_class — '안 보냄'과 '못 알아봄'을 가른다 (#112)

- **작업자**: @yooseongjin527
- **의도 · 목표**: `ua_class="unknown"` 이 성격이 다른 두 경우를 한 값으로 뭉개고 있었다 —
  **UA 헤더를 아예 안 보낸 것**과 **UA 는 왔는데 못 알아본 것**. 원문 UA 를 저장하지 않는
  설계라 **수집 시점에 안 가르면 그 정보는 영구히 사라진다.**
  결정적인 건 **같은 파일이 이미 그 구분을 하고 있었다**는 점이다 — `normalizeIntent()` 는
  40줄 거리에서 `null`(안 보냄)과 `"other"`(못 알아봄)를 섞지 않는다. 테스트 이름까지
  *"안 보낸 것과 못 알아본 것은 다르다"* 로 적혀 있다. 두 축이 다른 규칙을 쓰고 있었다.
- **조치**
  - `classifyClient()` 의 `if (!ua)` 분기가 **`no_ua`** 를 돌려준다. `unknown` 은 뜻이
    좁아졌을 뿐 그대로다(왔는데 못 알아봄).
  - **NULL 이 아니라 값으로 둔다.** 콘솔이 `ua_class IS NULL` 로 *"게이트웨이가 아직 이 축을
    안 싣는다"*(`axes_unfilled`)를 판정하기 때문에, NULL 로 두면 UA 없는 요청 하나가
    '축 미배선'으로 읽혀 카드가 통째로 미발행을 말한다. 테스트로 못박았다.
  - `migrations/0005` 의 컬럼 주석에 `no_ua` 추가 — **주석만이고 스키마는 안 건드렸다**
    (증분 규약상 적용된 마이그레이션의 DDL 은 고치지 않는다).
- **결과**
  - `npm test` **127 PASS · 0 FAIL** (기존 123 + 신규 4, partials 정합 OK).
  - **마이그레이션 없음** — `ua_class` 는 TEXT 라 값의 집합만 늘었다.
  - **과거 데이터는 소급하지 않는다.** 이미 쌓인 `unknown` 은 원문이 없어 되돌릴 수 없고,
    지어내면 `모른다 ≠ 0` 원칙을 스스로 어긴다. 실측 근거: prod 최초 트래픽에서 `unknown`
    10건이 4.1초에 몰렸고(Node 18+ global `fetch` 는 UA 를 안 보낸다) 그중 2건이 `/mcp`
    요청이었다 — **정의상 에이전트인데 '못 알아본 클라이언트'와 한 칸에 있었다.**
  - **남은 것**: `ops-dashboard/docs/reference/behavior-log-spec-draft.md` 가 `ua_class` 를
    6값으로 열거한다(7값이 됐다). 콘솔은 `CLASS_LABEL[…] || r.ua_class` 폴백이라 깨지지
    않고 슬러그로 보인다. **둘 다 콘솔 담당 소관이라 이 커밋에서 건드리지 않았다.**

  - 같은 이유의 칩은 **탭당 하나로 합치고** 표 이름을 나열한다(표마다 내면 시끄럽다)

    발행만 깨지는 날이 traffic 에 실제로 있다.
  - 줄머리에 분야별 성공률 + **추이 화살표**(창 앞·뒤 절반의 문제 점수 비교).
  - `GET /api/drill?domain=&day=` — 붉은 칸을 누르면 그날 그 분야의 실패 작업 · 발행 문제 ·
    빈 실행 · **재시도 끝에 성공**(성공률이 가리는 열화) · 오래 걸린 작업 · 단계별 집계.
  - 발행 대장은 UTC 라 **KST 로 접는다**(+9h) — 실행 축과 날짜 규약이 다르면 같은 칸에
    다른 날이 섞인다. 드릴은 요약과 **같은 환경 필터**를 쓴다.
- **결과**: 운영 D1 실측 7분야×7일 빨강 22칸. traffic 07/29 → 발행 문제 30건이 원본·발행·D1
  행수와 함께 펴진다. 닫기 동작 확인.
  > 당시 로컬 검증은 합성 픽스처로 했는데, **같은 날 뒤 작업에서 합성을 전면 배제**했다
  > (아래 "화면에서 모의 데이터를 걷어내고" 항목). 지금 로컬은 실호출 기록만 남아

### 원격 D1 배포 전 검사(preflight) 신설

- **작업자**: @Exisign · 판정 수정 @yooseongjin527 (PR #55)
- **의도 · 목표**: `migrations apply` 는 되돌리기가 어렵다. prod D1 은 62개 제품이 사는
  파이프라인의 DB 이고 **D1 Time Travel 은 DB 전체를 덮어쓴다** — 제품 publish 하나를
  되돌리면 발급된 키·쿼터·요청 로그가 같이 과거로 간다. "일단 돌려 보고 되돌린다"가 성립하지
  않는다. 그리고 `CREATE TABLE IF NOT EXISTS` 는 **이름이 같으면 모양이 달라도 조용히 넘어간다.**
- **조치**: 표가 "있는지"가 아니라 **모양(컬럼)이 같은지**를 본다. 기대 모양은
  `migrations/*.sql` 을 **인메모리 sqlite 에 실제로 적용**해 뽑는다(하드코딩 드리프트 없음).
  `모양 다름`이면 종료 코드 1 로 중단하고, **사람이 정한 뒤 `--ack "<사유>"` 로만** 통과한다
  — `--ack` 는 판정을 바꾸지 않고 사유를 함께 찍는다.
- **결과**
  - 구현 중 셋에 부딪혀 전부 주석에 사유를 남겼다 — Windows `.cmd` 래퍼를 Node 20+ 가
    막는 것(CVE-2024-27980), D1 이 상관 참조 `pragma` 를 막는 것(`SQLITE_AUTH`),
    표 89개를 한 문장에 물으면 길이 한도에 걸리는 것(ASAC-DAG#677 과 같은 함정).
  - 🔴 **판정에 구멍이 있었다** — FOREIGN 을 "우리 컬럼을 **전부** 가져야 인수됨"으로 봐서
    **dev 의 부분 오염**(`request_id` 하나만 얹힌 상태)을 통과시켰다. **이 스크립트를 만든
    이유가 그 사고인데 정작 사고 난 DB 를 정상으로 판정하고 있었다.**
    @yooseongjin527 이 `baseline`(남의 표의 원래 모양)을 함께 두고
    `우리 컬럼 ∩ 실제 − baseline` 으로 보도록 고쳤다(PR #55). 받았다.

### 요청 로그 표 개명 — `_request_log` → `_gateway_request_log`

- **작업자**: @yooseongjin527 (PR #53) · 결정은 #44 전원 확인
- **의도 · 목표**: 운영·개발 D1 에 게이트웨이 정본과 **다른 스키마**의 `_request_log` 가 이미
  있었고(`ts·path·query·token`), 그대로 배포하면 게이트웨이 INSERT 가 `ctx.waitUntil` 안에서
  실패해 **요청 로그가 전량 버려진다**. 조사 결과 **transit 워커가 계속 쓰기로** 확정돼,
  쓰는 쪽이 안 멈추므로 **게이트웨이가 이름을 비킨다**.
- **조치**: `0005` 를 **완성형 22컬럼 CREATE** 로(ALTER 물결 없음). 기존 표는 **DROP 도
  ALTER 도 하지 않는다**. 표 신설과 코드 전환을 **같은 커밋**에 — 30일 sweep
  `DELETE FROM _request_log` 가 코드 전환 없이 배포되면 transit 의 행을 지운다.
- **결과**
  - 🔴 이 과정에서 **`0004` 의 조건 없는 `ALTER` 가 이미 dev 의 남의 표에 얹혀 있던 것**이
    확인됐다. *"정본이 안 선 상태에서 ALTER 를 얹으면 어느 표에 붙는지가 배포 순서에
    좌우된다"* 가 가정이 아니라 **일어난 일**이었고, 그게 개명의 결정적 근거가 됐다.
  - 이름 후보 `_api_request_log` 는 **폐기** — 그 표는 네 문(`/api`·`/v1`·`/skill`·`/mcp`)이
    공유하는데 한 문 이름을 붙이면 나머지 셋이 설명되지 않는다.
